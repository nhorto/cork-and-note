# Auth flow fixes — sign-up, sign-in, password reset, transactional email

**Date:** 2026-09-10 · **Trigger:** owner QA pass on the TestFlight build
**Project:** `ixecayqpogkiawempzgc` · **Related:** epic [#160](../../issues/160), [`owner-checklist.md`](../business/owner-checklist.md) §C

Five separate problems turned up in one walk through the auth screens. Four are fixed; the fifth needs an account only Nick can open.

## What was reported

1. The back arrow on **Create account** could not be tapped.
2. Signing up did **not** sign you in — it bounced back to the login screen with "you can log in now".
3. **Confirm email** in the signup email opened `http://localhost:3000`.
4. **Reset password** opened `http://localhost:3000`, so the password could never be reset.
5. The emails are unbranded Supabase defaults.

## Root causes

The app code was mostly fine. **Three of the five were live Supabase project settings**, none of which are visible in this repo — which is why they survived the July review that fixed the app half of password reset (`2026-07-05-code-review.md` C2).

| # | Root cause |
|---|---|
| 1 | `app/register.js` positioned the back button at a hardcoded `top: 20`. On a notched iPhone the status bar is ~59pt tall, so the button sat *underneath* it and never received a touch. `app/forgot-password.js` had the same recipe at `top: 50` — inside the inset, but only just. |
| 2 | Auth → `mailer_autoconfirm` was **off**, so `signUp()` returns no session by design. The screen's fallback branch sent the user to `/login`. |
| 3 | `signUp()` passes no `emailRedirectTo`, so the confirmation link used **Site URL**, which was still the Supabase default `http://localhost:3000`. |
| 4 | `resetPassword()` *did* pass `redirectTo: 'corkandnote://reset-password'`, but the project's **redirect allow-list was empty**. GoTrue silently discards a redirect it has not been told to trust and falls back to Site URL — again `http://localhost:3000`. The app's `app/reset-password.js` handler was never reached. |
| 5 | No custom SMTP is configured, so mail goes out through Supabase's shared sender. |

Note on 3: the confirmation itself *worked*. The link hits `…supabase.co/auth/v1/verify` first, which marks the address confirmed and only then redirects. The dead localhost page was the last hop, not the verification — which is why sign-in started working afterwards.

## What changed

### Live project config (applied 2026-09-10, no rebuild needed)

```
site_url         http://localhost:3000  →  https://cork-and-note.vercel.app
uri_allow_list   (empty)                →  corkandnote://reset-password,
                                           corkandnote://auth-callback,
                                           https://cork-and-note.vercel.app/reset-password,
                                           https://cork-and-note.vercel.app/**
mailer_autoconfirm  false → true
```

Verified with `POST /auth/v1/admin/generate_link` (which validates against the allow-list but sends no mail): a recovery link now carries `redirect_to=corkandnote://reset-password`, while `https://evil.example.com/steal` is still rejected down to Site URL. **Password reset works on the already-installed TestFlight build** — the deep-link handler has shipped since PR #145.

`mailer_autoconfirm = true` is a deliberate product call for v1: no verification step, sign-up drops you straight into the app. It also takes email off the critical sign-up path, which matters while the sender is still rate-limited (below). The trade-off accepted: a typo'd address is an unrecoverable account, and we have no verified way to reach a user.

### App code

- `app/register.js` / `app/forgot-password.js` — back button positioned from `useSafeAreaInsets()` with a 44pt target (launch plan §3.3).
- `app/register.js` — when sign-up returns no session, the screen now attempts sign-in itself rather than redirecting to `/login`. With auto-confirm on, sign-up lands in the app; if verification is ever re-enabled, the flow degrades to a "check your inbox" alert instead of silently regressing.
- `app/login.js`, `app/register.js`, `app/forgot-password.js` — email is trimmed and lower-cased before it reaches Supabase. `" Nick@Example.com "` is a different (non-existent) account to GoTrue, and the user reads that as "my correct password was rejected".
- `app/login.js` — `textContentType` / `autoComplete` on both fields so the iOS keychain fills them.

### Email templates

`scripts/auth-emails.mjs` builds Royal Velvet HTML for the recovery, confirmation and email-change emails (table-based, inline styles, gold-ruled velvet header, `--push` uploads them via the Management API).

**They are not live yet.** Supabase rejects template edits with:

> Email template modification is not available for free tier projects using the default email provider. Please upgrade your plan or configure a custom SMTP provider.

So branded email is gated on SMTP, not on Supabase Pro — see below.

## Still open — needs Nick

**Custom SMTP is a launch blocker on its own**, separately from branding: the built-in sender is capped at **2 emails per hour across the whole project**. Three people forgetting their password in the same hour means the third gets nothing, and Supabase documents the shared sender as unsuitable for production.

Configuring any SMTP provider (Resend's free tier is 3,000/month) fixes all three at once — the rate limit, the `noreply@mail.app.supabase.io` sender, and the template lock. It needs a verified sending domain, so it is downstream of the `corkandnote.com` purchase already tracked in the owner checklist. Once it is live, `node scripts/auth-emails.mjs --push` puts the branded templates up.

Deferred, not blocking: a `/reset-password` page on the marketing site that bounces a desktop click into the app. Today the reset link only opens on the iPhone.
