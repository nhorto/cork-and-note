# Guest mode for App Review Guideline 5.1.1 (2026-09-21)

Epic #316. Sub-issues #317 (backend), #318 (session + guard), #319 (UI), #320 (build 30 + resubmission).

## The rejection

Submission `b410b0da` (1.0, build 29, submitted 2026-09-17) came back on 2026-09-21 with
**Guideline 5.1.1 Legal: Privacy - Data Collection and Storage**:

> The app requires users to register or log in to access features that are not account-based.
> Specifically, the app requires users to register before accessing journal feature. [...]
> Revise the app to let users freely access the app's features that are not account-based.

Only the app version item was rejected. The subscription group and both subscriptions were never
reviewed and fell back to `READY_TO_SUBMIT`, so they must be added to the next draft submission again.

## Root cause

`app/_layout.js` navigation guard: no session and outside the auth flow means `router.replace('/login')`.
Nothing was reachable without an account, including the winery directory, the map, and the sommelier,
none of which need an identity.

## Decision (owner, 2026-09-21)

Guest mode via Supabase anonymous sign-in. **No wall anywhere, only moments.**

| Question | Decision |
|---|---|
| First nudge to create an account | Once, after the first saved tasting (bottom sheet). Plus a dismissible Home card and a Sign in pill. Never on launch. |
| Can a guest buy Pro | Yes. Nudge to protect the subscription right after purchase. No wall on the buy button. |
| Sommelier for guests | Same free allowance as a Free account. |
| Guest logs a tasting | Saved under the guest id like any user. |
| Guest signs up | `updateUser({ email, password })` on the guest session. Same id, nothing to migrate. |
| Guest signs in to an existing account | Merge the guest's rows into that account (claim-token RPC). |

## Why anonymous auth, not a signed-out code path

`user.id` runs through 15 lib modules and all 16 RLS policies are `to authenticated`. An anonymous
Supabase user IS `authenticated`, so none of that changes. A true signed-out mode would have needed a
null-user branch in every module and an `anon` variant of every policy, right before a resubmission.

## How attribution works

- `auth.users.is_anonymous` is `true` for a guest and flips to `false` when an email is linked.
  Count guests vs converted straight off that column.
- **Sign up from a guest session**: `linkGuestAccount` calls `auth.updateUser`. The project
  auto-confirms email, so the link lands immediately and a password sign-in works straight away.
  Verified live on production 2026-09-21: same id before and after, rows intact, `is_anonymous=false`.
- **Sign in to an existing account from a guest session**: `signInFromGuest` calls
  `stamp_guest_claim()` while still a guest (returns a one-shot token), then `signInWithPassword`,
  then `merge_guest_account(guest_id, token)` as the real user. The RPC checks the token, that the
  claim is under an hour old, and that the guest is still anonymous; it moves 16 content tables,
  dedupes `favorites` / `wishlist` on their unique keys, re-owns storage objects, and deletes the
  guest user. Quota tables (`chat_usage`, `places_usage`) and `entitlements` are not moved on purpose.
  Verified live 2026-09-21: rows moved, replay rejected.

## Backend changes (applied to production 2026-09-21, migration `20260921120000_guest_accounts`)

- `external_anonymous_users_enabled: true` via the Management API.
- `public.users.email` made nullable. It was `NOT NULL` and `handle_new_user()` inserted `new.email`
  verbatim, so an anonymous sign-in failed with "Database error saving new user" until this.
- `on_auth_user_email_linked` trigger copies the linked email (and name) into `public.users`.
- `guest_claims` table (no policies; RPC only), `stamp_guest_claim()`, `merge_guest_account()`.

## App changes

- `lib/guest.js`: `isGuestUser`, `startGuestSession`, `linkGuestAccount`, `signInFromGuest`, nudge
  bookkeeping. Tests in `__tests__/guest.test.js`.
- `app/_layout.js`: no session at boot mints a guest; guard lets guests onto the auth screens;
  `AuthContext` gains `isGuest` and `continueAsGuest`; `signUp` links when a guest; `signIn` merges
  when a guest; `signOut` lands on Home as a fresh guest.
- `app/login.js`: back button for guests; "Continue without an account" only when there is no
  session at all (offline first launch).
- `app/(tabs)/home.js`: Sign in pill instead of the avatar, `GuestAccountCard`, `AccountNudgeSheet`.
- `app/(tabs)/profile.js`: guest header, Create account / Log in, no sign-out row.
- `app/profile/account-settings.js`: no change-password / delete-account rows for guests.
- `app/paywall.js`: post-purchase "Protect your subscription" nudge for guests.
- `app/log-session.js`: a guest's first saved tasting arms the one-time sheet.
- `components/AgeGate.js`: Terms / Privacy acknowledgement at the door (guests never see the register clickwrap).

## Known limits

- A guest who deletes the app loses their guest session and therefore their journal. That is the
  honest reason to create an account, and it is what the card and sheet say.
- Anonymous sign-ins are rate limited by Supabase (30/hour per IP). Guest AI usage is metered
  per guest id like a Free account. Revisit if throwaway guests show up in the chat costs.
- Guest auth rows accumulate. A cleanup of anonymous users older than N days with no rows can be
  added later; nothing depends on it for launch.
